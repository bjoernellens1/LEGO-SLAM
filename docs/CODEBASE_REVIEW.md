# LEGO-SLAM Codebase Review

## Scope

This document reviews the repository from an implementation perspective rather than the paper perspective. It focuses on:

- pipeline structure
- important modules and methods
- runtime dependencies
- major tunables
- practical extension points
- notable implementation caveats

## Executive Summary

LEGO-SLAM is structured as a two-process RGB-D SLAM system:

1. `mp_Tracker.py` performs frame-by-frame pose tracking with `pygicp.FastGICP`.
2. `mp_Mapper.py` owns the global Gaussian map, keyframe refinement, semantic-feature supervision, pruning, evaluation, and loop closing.

Despite the top-level code defining a `LoopManager` process entrypoint, loop closing is not run as a third worker. In the current implementation it is instantiated and executed synchronously inside the mapper.

The system is best understood as a fusion of three subsystems:

- geometric tracking from RGB-D point clouds and G-ICP
- differentiable 3D Gaussian map optimization
- semantic feature handling based on precomputed LSeg features, optionally compressed from 512D to 16D for speed

## Repository Layout

### Core runtime

- `lego_slam.py`: main entrypoint, argument parsing, shared-memory setup, process launch
- `mp_Tracker.py`: online tracking and keyframe selection
- `mp_Mapper.py`: Gaussian map management, training loop, evaluation, loop closure orchestration
- `mp_Loopmanager.py`: language-assisted loop candidate selection, GICP verification, pose graph optimization

### Scene and rendering

- `scene/gaussian_model.py`: Gaussian parameter storage, optimizer integration, pruning, persistence
- `scene/shared_objs.py`: shared-memory camera and Gaussian exchange objects; lightweight encoder/decoder modules
- `gaussian_renderer/`: differentiable Gaussian rasterization wrappers used for RGB, depth, alpha, and semantic rendering

### Utilities

- `utils/traj_utils.py`: dataset-specific trajectory loading and frame association
- `utils/PGO.py`: GTSAM-based pose graph builder/optimizer
- `utils/loss_utils.py`: RGB/depth/feature losses
- `utils/undistort_feature_img.py`: undistortion of stored semantic feature maps

### Semantic preprocessing

- `run_encoding.sh`: batch feature extraction wrapper
- `Lseg/`: LSeg model and preprocessing code
- `encoding/`: PyTorch-Encoding dependency vendored into the repo

### Native / external submodules

- `submodules/diff-gaussian-rasterization-feature`: custom rasterizer with semantic feature output
- `submodules/fast_gicp`: GICP backend exposed as `pygicp`

## End-to-End Pipeline

### 1. Offline semantic preprocessing

Before SLAM runs, per-frame semantic feature maps are generated by:

- `run_encoding.sh`
- `Lseg/encode_images.py`

Output is stored under `rgb_feature_langseg/` as `.pt` tensors. For TUM and ScanNet, these feature maps are then undistorted with `utils/undistort_feature_img.py`.

This is a hard runtime dependency. The SLAM system expects feature-map filenames to align with the RGB image naming convention.

### 2. System bootstrap

`lego_slam.py` does the following:

- reads camera/config text files
- determines image size, intrinsics, distortion, depth scaling, and dataset type
- creates shared-memory transport objects
- loads one test frame to size the shared buffers
- constructs optional semantic encoder/decoder modules
- instantiates tracker and mapper
- launches two multiprocessing workers

Important detail: only tracker and mapper are launched. The loop-closing worker is commented out in `LEGO_SLAM.run()`.

### 3. Tracking worker

The tracker:

- loads all RGB and depth frames at startup
- converts the current RGB-D frame into a downsampled point cloud
- aligns the current frame to the current target map with FastGICP
- decides whether the frame becomes a tracking keyframe or a mapping keyframe
- sends new Gaussians and the current camera to the mapper through shared memory

Tracking is strictly geometric. Semantic features are only moved around as frame metadata for the mapper.

### 4. Mapper worker

The mapper owns the persistent scene state:

- initializes the first Gaussian map
- converts per-pixel semantic maps to per-point features
- refines keyframe poses by rendering the current Gaussian map and optimizing camera deltas
- inserts new Gaussians into the global model
- trains Gaussian appearance, geometry, opacity, and semantic features
- optionally performs loop closing
- computes evaluation metrics
- saves outputs

The mapper is the architectural center of the repository.

### 5. Loop closure

Loop closure is mapper-driven:

- the mapper converts semantic feature maps into histogram descriptors using a precomputed codebook
- candidate historical keyframes are selected by semantic histogram similarity and proximity
- candidates are verified by GICP against a local Gaussian-derived submap
- accepted constraints are inserted into a GTSAM pose graph
- optimized keyframe poses are propagated back into both camera objects and the Gaussian map

### 6. Output and evaluation

At the end of mapping, the system can:

- save `scene.ply`
- save learned CNN decoder and optional encoder checkpoints
- compute ATE with `evo`
- compute PSNR, SSIM, LPIPS, and semantic agreement metrics

## Process and Dataflow Model

### Shared objects

The tracker and mapper communicate through shared PyTorch tensors in `scene/shared_objs.py`:

- `SharedCam`: current keyframe camera state plus current semantic feature map
- `SharedGaussians`: newly proposed Gaussians from tracker to mapper
- `SharedTargetPoints`: recent trackable Gaussians from mapper back to tracker
- scalar flags: synchronization between workers

The design is simple but uses busy waiting:

- multiple loops poll shared flags with `time.sleep(1e-15)`

This works, but it is CPU-inefficient and not especially robust under load.

### Camera state convention

The system frequently stores both:

- `c2w` camera-to-world
- `R`, `t` from `w2c`

`SharedCam.update_pose()` applies an SE(3) delta in `w2c` space, then reconstructs `c2w`.

### Point/feature flow

Per tracking keyframe, the flow is:

1. RGB-D frame to point cloud in tracker
2. GICP provides local covariance-derived rotations/scales
3. tracker writes candidate Gaussians plus keyframe pose into shared memory
4. mapper reads the feature map from `SharedCam`
5. mapper downsamples semantic features to point locations
6. mapper optionally compresses 512D features to 16D with `CNN_encoder`
7. mapper inserts new Gaussians into the global model

## Core Modules and Important Methods

### `lego_slam.py`

### Responsibilities

- parse CLI arguments
- load camera config
- initialize shared runtime state
- start tracker and mapper workers

### Important methods

- `LEGO_SLAM.__init__`
  - copies CLI args into SLAM state
  - reads camera parameters
  - allocates shared buffers
  - constructs optional encoder/decoder
- `LEGO_SLAM.run`
  - launches tracker and mapper processes
- `LEGO_SLAM.get_test_image`
  - dataset-specific first-frame loader used for shared-memory sizing
- `LEGO_SLAM.set_downsample_filter_multires`
  - precomputes dense and sparse pixel sampling grids

### Architectural note

The existence of `self.loop_manager` at the top level is slightly misleading. The actual loop-closing logic that affects the map is executed inside `mp_Mapper.py`.

### `mp_Tracker.py`

### Responsibilities

- dataset loading
- frame-to-map registration
- keyframe decision logic
- creation of candidate Gaussians for mapper

### Important methods

- `Tracker.tracking`
  - main online loop
  - initializes the first target point cloud
  - runs GICP alignment for subsequent frames
  - decides between tracking keyframe and mapping keyframe
  - waits for mapper feedback on refined poses and updated target Gaussians
- `Tracker.get_images`
  - dataset-specific RGB/depth/feature path loading
- `Tracker.downsample_and_make_pointcloud2`
  - converts depth into dense and sparse point clouds
  - computes invalid regions from borders, large depths, and extreme brightness
- `Tracker.eliminate_overlapped2`
  - filters out points already sufficiently explained by the map
- `Tracker.quaternion_multiply`
  - composes GICP-estimated local rotations with camera pose rotation

### Key tracker behaviors

- first frame is seeded from the dataset ground-truth pose in `TrajManager`
- TUM uses a higher GICP minimum iteration count
- recent trackable Gaussians from mapper are sent back as the next target map

### Keyframe policy

Tracking keyframe insertion is driven by overlap:

- if correspondence overlap falls below `keyframe_th`, a tracking keyframe is created
- otherwise, periodic mapping keyframes are created every `keyframe_freq` frames since the last tracking keyframe

This means the system mixes:

- geometry-triggered keyframes
- cadence-triggered training-only keyframes

### `mp_Mapper.py`

### Responsibilities

- global Gaussian map ownership
- semantic supervision
- pose refinement
- map training
- pruning
- loop closure
- metric computation

### Important methods

- `Mapper.mapping`
  - main worker loop
  - initializes the Gaussian map
  - consumes new keyframes
  - runs per-keyframe pose refinement
  - inserts Gaussians
  - trains map and optional feature compressor
  - invokes loop closure
- `Mapper.generate_and_store_histogram`
  - converts the current semantic feature map into a normalized histogram descriptor
- `Mapper.is_encoder_period`
  - decides whether training is in decoder mode or encoder-only mode
- `Mapper.update_gs_mapper`
  - propagates pose graph updates into the Gaussian model and in-memory cameras
- `Mapper.eval_ate`
  - dataset-specific trajectory evaluation with `evo`
- `Mapper.calc_2d_metric`
  - RGB and perceptual metric evaluation against optimized poses

### Mapper loop phases

#### Initial map creation

The first tracking keyframe:

- creates the initial `GaussianModel`
- initializes Gaussian color from RGB
- initializes scale from GICP scale normalized by depth
- initializes semantic features from the current LSeg map if enabled

#### Per-keyframe pose refinement

For both tracking and mapping keyframes:

- render the current Gaussian map from the new keyframe
- compare rendered RGB and depth against the observed frame
- optimize camera delta for up to 10 iterations
- accept pose refinement only when masks and residuals are reasonable

This refinement is local and photometric/geometric, not graph-based.

#### Training loop

The training loop samples keyframes from `mapping_cams` and optimizes:

- Gaussian position
- SH appearance coefficients
- opacity
- scale
- rotation
- semantic feature vectors
- optional decoder or encoder weights

Loss terms are:

- RGB L1 + DSSIM
- depth L1
- semantic feature L1

#### Speedup mode

If `--speedup` is enabled:

- Gaussian semantic features live in `point_feature_dim` space, default 16D
- `CNN_decoder` maps 16D rendered features back to 512D for supervision
- optional `CNN_encoder` learns the inverse compression

This is the main mechanism that reduces semantic rendering cost.

### Loop closure integration

Loop closing is initiated only on tracking keyframes and only after enough history exists. When active:

- histograms are stored per keyframe
- the current keyframe is tested against older tracking keyframes
- successful pose graph updates trigger Gaussian transforms and camera updates

### Map retention policy

`mapping_cams` is capped by `max_mapping_keyframes`.

Eviction policy:

- remove oldest mapping keyframes first
- if none remain, remove an older tracking keyframe from the older half of the buffer

This buffer controls optimization memory, not the persisted global Gaussian map.

### `mp_Loopmanager.py`

### Responsibilities

- semantic loop candidate generation
- geometric verification
- pose graph optimization

### Important methods

- `LoopManager.insert_new_kf`
  - stores the latest tracking keyframe for loop testing
- `LoopManager.loop_detection_language_feature`
  - compares semantic histograms with older tracking keyframes
  - keeps top semantic candidates
- `LoopManager.calculate_loop_constraints`
  - verifies candidates by GICP against a cropped submap
  - accepts only the best high-overlap candidate
- `LoopManager.pgo_update`
  - builds and optimizes the GTSAM pose graph

### Loop candidate logic

Candidates are filtered by:

- keyframe age: recent tracking keyframes are excluded by `loop_closing_start`
- spatial proximity: squared position distance must be less than `1.0`
- semantic similarity: cosine similarity over histogram descriptors must exceed `0.7`

Only the top semantic candidates are geometrically verified.

### Geometric verification logic

Candidate verification uses:

- a Gaussian-derived submap around the candidate keyframe
- coarse GICP with global correspondence distance
- local GICP refinement with a tighter distance
- projection-filtered overlap scoring

Acceptance is strict:

- only the best candidate with overlap above `0.9` is turned into a loop factor

### `scene/gaussian_model.py`

### Responsibilities

- stores the global Gaussian parameter tensors
- owns the optimizer and optimizer state surgery
- supports adding, pruning, transforming, and saving Gaussians

### Important methods

- `GaussianModel.create_from_pcd2_tensor`
  - initializes the first map from a point cloud and optional semantic features
- `GaussianModel.add_from_pcd2_tensor`
  - appends new Gaussians from later keyframes
- `GaussianModel.get_trackable_gaussians_tensor`
  - returns recent, trackable, opaque Gaussians for tracker targets
- `GaussianModel.transform_gaussians`
  - applies loop-closure pose corrections to Gaussians associated with a keyframe
- `GaussianModel.training_setup`
  - creates the optimizer and learning-rate schedule
- `GaussianModel.prune_large_transparent_and_lang`
  - removes low-opacity, over-large, and semantically redundant Gaussians
- `GaussianModel.save_ply`
  - exports the final Gaussian map, including semantic channels

### Parameterization notes

- color uses spherical harmonics
- opacity is stored in inverse-sigmoid space
- scaling is stored in log space
- semantic feature vectors are stored per Gaussian
- each Gaussian carries:
  - keyframe ownership
  - trackable mask
  - edge mask

### Pruning strategy

The custom pruning path combines:

- opacity thresholding
- scale thresholding
- sampled semantic redundancy pruning based on spatial distance and cosine similarity

This pruning routine is one of the main LEGO-SLAM-specific modifications relative to a plain 3DGS mapper.

### `scene/shared_objs.py`

### Responsibilities

- defines shared camera and Gaussian transport containers
- provides SE(3) update utilities for camera refinement
- defines the lightweight semantic encoder/decoder networks

### Important methods

- `SharedCam.setup_cam`
  - writes the new camera pose and frame content into shared memory
- `SharedCam.get_semantic_feature_cuda`
  - exposes the current frame semantic tensor to the mapper
- `SharedCam.update_pose`
  - applies learned SE(3) delta to the camera pose
- `CNN_encoder.forward`
  - compresses 512D semantic features to point-feature space
- `CNN_decoder.forward`
  - expands rendered point-feature space back to 512D supervision space

### Important design detail

`SharedCam` eagerly loads the current feature-map file from disk and keeps it attached to the current camera object. That avoids repeated disk reads inside the main mapping loss, but it means the feature map for each newly shared keyframe is loaded immediately.

## Rendering Path

`gaussian_renderer/__init__.py` wraps the custom rasterizer and exposes:

- `render`
- `render_2`
- `render_3`
- `render_3_filtered`

The mapper mainly uses `render_3`, which returns:

- RGB render
- depth render
- semantic feature render
- alpha image
- screen-space point gradients

This render result is the basis for:

- pose refinement
- Gaussian training losses
- visibility-aware filtering

## Tunables

- `overlapped_th`

## Dataset-Specific Launch Defaults

The provided shell scripts encode recommended defaults.

### Replica

- tighter tracking distance: `max_correspondence_distance=0.02`
- coarser downsampling: `downsample_rate=10`
- smaller loop-closing distances
- `loop_closing_start=10`

### TUM

- `downsample_rate=5`
- `max_correspondence_distance=0.03`
- moderate loop-closing thresholds

### ScanNet

- `downsample_rate=5`
- `max_correspondence_distance=0.05`
- much larger `edge_weight=10.0`
- stronger loop-closing search radius
- smaller `n_trackable_keyframes=25`

These script defaults are a useful summary of how sensitive the system is to dataset characteristics.

## Practical Extension Points

### Replacing the semantic backbone

The cleanest replacement path is:

1. keep the `rgb_feature_langseg/*.pt` convention
2. emit per-pixel feature tensors with stable dimensionality
3. update `semantic_feature_dim` and the optional encoder/decoder dimensions if needed

Because the mapper consumes stored tensor files rather than invoking the backbone online, semantic extraction is already decoupled from SLAM runtime.

### Changing loop descriptors

The current loop descriptor is:

- codebook assignment over 512D per-pixel semantic features
- normalized histogram over visual words

This can be replaced without rewriting the entire loop manager, as long as:

- per-keyframe descriptors can still be generated in the mapper
- the loop manager can compare descriptors and rank candidates

### Changing the front-end registration

The tracker is strongly coupled to `pygicp.FastGICP`, but the handoff boundary is clear:

- input: downsampled points plus invalid masks
- output: aligned pose, point covariances, rotations, scales, and correspondences

Replacing GICP would require preserving these outputs or adapting the Gaussian initialization path.

## Notable Implementation Caveats

### 1. Loop closure is not a separate process

Even though `lego_slam.py` defines a loop-closing worker, only tracker and mapper are launched. Actual loop closure is synchronous inside the mapper. Anyone expecting a three-worker architecture should not rely on that assumption.

### 2. `--rerun_viewer` disables final save path in practice

Mapper output saving is gated by:

- `save_results`
- and `not rerun_viewer`

The provided run scripts often pass both `--save_results` and `--rerun_viewer`, which means the final `scene.ply` is not written under that path.

### 3. Synchronization is polling-based

Tracker and mapper use shared flags with very tight busy waits. This is simple, but it is not ideal for CPU efficiency or debuggability.

### 4. Camera config headers are inconsistent

The parser relies on fixed field ordering rather than header names. The numeric data is what matters.

### 5. Tracker bootstraps from dataset GT pose

The first pose is seeded from `TrajManager.gt_poses[0]`. This is convenient for experiments, but it is not a pure unknown-initial-pose SLAM setup.

### 6. Semantic feature supervision is tightly integrated into mapping

If semantic files are missing or dimensionally inconsistent, large parts of the mapper path fail, especially in `semantic_feature_init` and `speedup` mode.

### 7. Memory pressure can become significant

Main contributors:

- full-frame RGB/depth preloading in the tracker
- pinned semantic feature tensors
- the global Gaussian map
- optional 512D feature supervision
- active camera buffer in the mapper

`max_mapping_keyframes`, `downsample_rate`, and `speedup` are the first controls to reach for.

## Running Without Embeddings

### Short answer

The repository now supports an embeddings-off comparison mode through `--disable_embeddings`.

That mode is intended for RGB-D-only comparison runs. It:

- disables semantic feature loading
- disables semantic supervision in mapper training
- switches pruning to geometry/opacity-only pruning
- auto-disables language-based loop closing
- auto-disables semantic evaluation

The underlying geometric tracker and Gaussian mapper are left intact.

What already works without semantics:

- tracking is geometric and uses GICP only
- keyframe pose refinement uses RGB and depth only
- Gaussian colors, opacity, scale, and pose optimization do not fundamentally require semantic losses

Without that flag, the default semantic path still assumes semantic features exist:

- `SharedCam` eagerly loads per-frame feature maps from `rgb_feature_langseg/`
- mapper training always computes a semantic feature loss in the main optimization loop
- language-based pruning uses Gaussian semantic features
- loop closing depends on semantic histograms

So the current code is not "semantics optional". It is "semantics deeply integrated, but not required for every subsystem".

### Why tracking would still work

`mp_Tracker.py` does not use semantic tensors for registration. Its key operations are:

- RGB-D to point cloud conversion
- GICP alignment
- overlap-based keyframe insertion
- handoff of new Gaussians and camera pose to mapper

That means front-end odometry does not depend on embeddings.

### Why mapper mostly would still work

Two important mapper stages are already non-semantic:

- keyframe rendering-loss pose refinement uses RGB and depth only
- the Gaussian model already supports creation with `semantic_feature=None`, in which case semantic channels are zero- or Xavier-initialized

This strongly suggests that a comparison mode with:

- RGB loss
- depth loss
- no semantic loss
- no language pruning
- no language loop closure

should be viable without changing the overall architecture.

### What the new flag changes

#### 1. `SharedCam` feature loading is skipped

`scene/shared_objs.py` no longer loads per-frame feature maps when `--disable_embeddings` is set.

#### 2. Mapper training falls back to RGB + depth loss

The main training loop in `mp_Mapper.py` skips semantic loss entirely in embeddings-off mode and optimizes only:

- RGB reconstruction
- depth reconstruction

#### 3. Pruning becomes geometry-only

The periodic pruning call switches from `prune_large_transparent_and_lang` to `prune_large_and_transparent`.

#### 4. Loop closing is forced off

The implemented loop candidate generation depends on histogram descriptors from semantic feature maps, so `--disable_embeddings` also forces `--enable_loop_closing` off.

### Recommended implementation strategy

The practical path is not to remove semantic tensors from the renderer. That would be a larger change because the custom rasterizer and Gaussian data model both expect semantic channels.

Instead, add an "ignore semantic supervision" mode:

1. keep semantic channels allocated in the Gaussian model
2. initialize them to zeros
3. skip loading per-frame feature maps
4. skip semantic loss
5. disable semantic pruning
6. disable language loop closure
7. skip semantic evaluation

This gives a fair geometric baseline with minimal architectural disruption.

### Estimated implementation difficulty

#### Moderate for a usable comparison mode

Estimated scope:

- `lego_slam.py`
- `scene/shared_objs.py`
- `mp_Mapper.py`
- optionally `mp_Loopmanager.py`

Likely effort:

- small to medium patch
- no native code changes required if semantic tensors remain allocated

This repository now implements that approach with `--disable_embeddings`.

#### Hard for a fully semantic-free renderer/data model

If the goal is to remove semantic dimensions entirely from:

- Gaussian storage
- rasterizer inputs/outputs
- renderer wrappers

then the effort becomes significantly larger because it touches the custom rasterization submodule and multiple shape assumptions in the Python code.

That is not the recommended path for a comparison experiment.

### Bottom line

For comparison experiments, an embeddings-off mode is feasible and not especially risky.

The right implementation is:

- keep the same tracker
- keep the same Gaussian mapper
- disable semantic supervision and semantic-only features
- compare against the full system

That should be a moderate change, not a rewrite.

## Bottom Line

The codebase is organized around a clear split:

- tracker for geometry and keyframe production
- mapper for everything stateful and expensive

The two distinctive LEGO-SLAM features are:

- semantic-feature-aware Gaussian optimization, including 16D speedup mode
- language-informed loop candidate generation and semantic redundancy pruning

If you need to modify behavior safely, the highest-leverage files are:

- `mp_Tracker.py` for front-end behavior
- `mp_Mapper.py` for optimization behavior
- `scene/gaussian_model.py` for map representation and pruning
- `mp_Loopmanager.py` for loop-closing behavior
